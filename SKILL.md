# Learn Skill: Agent Memory & Continuous Learning

Extract knowledge worth keeping from a session and persist it so future sessions start smarter. Prefer a one-line rule. When a reusable command sequence or structural map would serve better, add a project script or an architecture note instead.

The slash command is `/learn-skill`. Saying `/learn` or "remember this" is the same trigger.

---

## 1. When to run

- The user explicitly asks: `/learn-skill`, `/learn`, "remember this", "save this rule", "forget this", "unlearn", or "do we still need this".
- The user corrects the agent, or repeats a preference they have stated before.
- A non-obvious configuration, architecture decision, or debugging fix was resolved and would cost real time to rediscover.
- A session is wrapping up and should be reviewed for anything durable — and for learned rules that are no longer true.

If nothing clears the quality bar, say so and write nothing. An empty result is a valid outcome.

---

## 2. Is it worth learning?

Save a candidate only if **all four** are true:

1. **Durable** - still true next week, and next session. Not tied to the current task, branch, or ticket.
2. **Actionable** - changes what an agent would do. A rule that no future action depends on is trivia.
3. **Recurring** - the situation will plausibly come up again.
4. **Non-obvious** - a competent agent would not already infer it from the code, the docs, or common practice.

**Never save:**
- Secrets: API keys, tokens, passwords, connection strings, private URLs.
- Personal identifiers or anything the user would not want written to a file that may be committed.
- Transcript excerpts, task status, or session narration. Memory holds rules and maps, not history.
- Facts already discoverable in the repo (dependency versions, file locations, existing config).

**Do not save:**
- One-off instructions scoped to the current request ("skip tests just this once").
- Speculation about preferences the user never actually stated.
- Restatements of a rule already in memory.
- Time-boxed focus or status ("focusing on networking for a few days", "this week we are on auth", "currently debugging X"). If it will be stale next week, it is not a rule. Leave it in the chat.

When a candidate is borderline, keep it out of the proposal or mark it as optional.

### Examples

| Candidate | Verdict |
| :--- | :--- |
| "Never edit files under `vendor/`; they are generated by `make vendor`." | Rule |
| "Use HSL rather than hex for all CSS color values." | Rule |
| "On this codebase, `pytest` must run via `uv run pytest` or imports fail." | Rule |
| A 15-step vendor refresh the user will run again | Script plus a one-line rule that points at it |
| How the API, workers, and queue fit together | Architecture note, not a rule |
| "The user is refactoring `auth.py` today." | Skip |
| "The user is focusing on networking for a few days." | Skip — and remove it if it is already in memory |
| "The project uses TypeScript." | Skip |
| "Write clean, readable code." | Skip |

## 3. What to persist

Pick the smallest artifact that will help next time. Details: [references/artifacts.md](references/artifacts.md).

| Artifact | Destination | Use when |
| :--- | :--- | :--- |
| **Rule** | `## Learned Rules` in the memory file | One imperative line changes future behavior |
| **Script** | Project `scripts/` | A reusable command sequence was actually run and will be needed again |
| **Architecture note** | Existing `architecture.md` or `docs/architecture.md` | Structural facts that are too large for one line and will be read on demand |

Do not invent scripts or an architecture file speculatively. A rule that points at a new script is usually the right pair: the rule stays cheap, the procedure lives in the script.

---

## 4. Memory scopes

| Scope | Destination | Holds |
| :--- | :--- | :--- |
| **Project** | `AGENTS.md` at the git root | Repo conventions, build/test invocations, pointers to scripts |
| **Global** | The rules file this IDE already loads | User-wide preferences |
| **Custom** | A path the user named | Any harness with its own memory location |

Users only type `/learn-skill` (or say "remember this"). They never pass flags. Infer the current IDE yourself and write global rules to the file it actually loads: Cursor → `~/.cursor/rules/learned.mdc`; Claude Code → `~/.claude/CLAUDE.md`; Codex → `~/.codex/AGENTS.md`; Gemini → `~/.gemini/GEMINI.md`. The CLI `--harness` flag is an implementation detail for that write — do not ask the user which harness they are in. If you omit it, the script picks Cursor when `~/.cursor` exists, then Claude, Codex, Gemini.

Project writes resolve the git root from `--workspace` or the current directory, then use that `AGENTS.md`. Nested package `AGENTS.md` files are only used when `--workspace` points at that package.

Learned rules go under `## Learned Rules`. Never rewrite or reorder content outside that section.

Precedence: current-turn instruction > project memory > global memory.

---

## 5. Rule format

One rule per bullet, imperative voice, one line. Add a short rationale in parentheses only when the reason is not self-evident.

Prefer these category headings: `Architecture`, `Build & Test`, `Conventions`, `Editor`, `Git`, `Security`, `Styling`, `Testing`, `Tooling`, `General`. Add a new heading only when none of those fit.

```markdown
## Learned Rules

### Styling
- Use HSL rather than hex for CSS color values (keeps the theme tokens interpolatable).

### Build & Test
- Run pytest via `uv run pytest`; a bare `pytest` resolves the wrong interpreter.
```

Good: `Never edit files under vendor/; regenerate them with make vendor.`
Bad: `Be careful with the vendor directory.`
Good: `Refresh vendors with python scripts/vendor_sync.py.`
Bad: `The user said in this session that they like composition sometimes.`

Keep `AGENTS.md` small. It is injected into context every session.

## 6. Workflow

**Step 1 - Scan.** Review the session for constraints, corrections, hard-won fixes, and reusable procedures.

**Step 2 - Filter.** Apply section 2. Discard anything that fails.

**Step 3 - Choose artifact and scope.** Phrase rules in the section 5 format. Route leftovers to a script or architecture note only when section 3 says so.

**Step 4 - Reconcile and prune.** Read project and global learned rules (`--action list` on both). Skip duplicates. If a new rule contradicts an existing one, propose a replace. If several overlap, propose one consolidated line and removals.

Then ask of every existing bullet: would I still save this under section 2? If no — time-boxed, contradicted by this session, or the user said they do not need it — add a **Remove** row. Do not wait for a separate prune command. `/learn-skill` always reviews memory, not only additions. Details: [references/pruning.md](references/pruning.md).

**Step 5 - Propose. Do not write yet.** Show a short table and wait:

| Type | Scope | Destination | Change |
| :--- | :--- | :--- | :--- |
| Rule | project | AGENTS.md / Build & Test | Run tests with `uv run pytest`. |
| Remove | project | AGENTS.md | User is focusing on networking for a few days. |
| Script | project | scripts/vendor_sync.py | Refresh vendored deps the way we just did. |
| Architecture | project | docs/architecture.md | How the API, workers, and queue fit together. |

Ask the user to accept all, accept some, edit, or skip. If the only items are removals, still propose them. If nothing to add or drop, say that and stop.

**Write immediately only when** the user already said "learn and save", "just save", or "don't ask".

**Step 6 - Write** the confirmed items. Run the CLI from **this skill's directory** (the folder that contains this `SKILL.md`), not from the project `scripts/` folder. On Windows, if `python` is missing, use `py -3`.

```bash
python "<skill-dir>/scripts/memory_manager.py" --action list --scope project
python "<skill-dir>/scripts/memory_manager.py" --action append --scope project --category "Build & Test" --content "Run pytest via 'uv run pytest'; a bare pytest resolves the wrong interpreter."
python "<skill-dir>/scripts/memory_manager.py" --action replace --scope project --match "Old rule." --content "New rule."
python "<skill-dir>/scripts/memory_manager.py" --action remove --scope project --match "Stale rule."
python "<skill-dir>/scripts/memory_manager.py" --action append --scope global --category "Editor" --content "Prefer HSL over hex for CSS color values."
```

The script creates `## Learned Rules` / `### <category>` as needed and skips exact duplicates. For scripts and architecture notes, write those files directly using [references/artifacts.md](references/artifacts.md). If a new script should change default behavior, also append a one-line rule that points at it.

**Step 7 - Report.** List what was written and where. If the user declined, write nothing.
